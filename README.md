# Сервис генерации

Принимает заказ, списывает токены, отдаёт задачу провайдеру (`alpha`/`beta`), при отказе идёт на следующую «ногу», а если отказали все, возвращает токены. Каждое движение денег происходит ровно один раз; это обеспечивает PostgreSQL, а не аккуратность кода (см. [«Ровно один раз»](#ровно-один-раз-начисление-и-возврат)).

Стек: Python 3.12, FastAPI, asyncpg и сырой SQL (все критичные места это `FOR UPDATE`, `ON CONFLICT`, условные `UPDATE ... RETURNING`; ORM скрывал бы момент, когда берётся блокировка), PostgreSQL 16.

## Запуск

Нужен только Docker с Compose v2, больше ничего ставить не надо.

```bash
cp .env.example .env      # необязательно: без .env работают значения по умолчанию
docker compose up --build
```

Поднимаются `db`, одноразовый `migrate`, `api` (uvicorn, 4 воркера, в каждом свой сторож), фейковые провайдеры `alpha` и `beta`. Готово, когда `docker compose ps` показывает `api`, `alpha`, `beta`, `db` как `healthy`, а Swagger открывается на http://localhost:8000/docs. Остановить: `docker compose down` (`-v` дополнительно удалит данные БД).

Запустить сервис и сразу прогнать e2e-тесты одной командой: `./run.sh` (подробности в разделе [«Тесты»](#тесты)).

| Сервис | Порт на хосте | Переопределение |
|---|---|---|
| api | 8000 | `API_PORT` |
| alpha | 8001 | `ALPHA_PORT` |
| beta | 8002 | `BETA_PORT` |
| db | 5432 | `DB_PORT` |

Если порт на хосте занят (`address already in use`), поменяйте его в `.env` (шаблон со всеми переменными и комментариями: [`.env.example`](.env.example); сам `.env` в `.gitignore`) или передайте переменной окружения, например `DB_PORT=55432 docker compose up`. Внутри сети compose порты не меняются, тестам это не мешает.

`WEBHOOK_SECRET` берётся из `.env`, а если его нет, из значения по умолчанию `test-secret` в `docker-compose.yml`. Это известное dev-значение. У самого приложения значения по умолчанию нет: без переменной оно не стартует. Для любого реального развёртывания секрет нужно переопределить в `.env`. Тогда в примере ниже поменяйте и `SECRET`.

### Пример: оплата, заказ, статус

Подпись `X-Signature` это HMAC-SHA256 сырого тела запроса, один общий секрет для провайдеров и оплат.

```bash
API=http://localhost:8000          # или http://localhost:$API_PORT
SECRET=test-secret
sign() { python3 -c 'import hmac,hashlib,sys; print(hmac.new(sys.argv[1].encode(), sys.argv[2].encode(), hashlib.sha256).hexdigest())' "$SECRET" "$1"; }

# 1. оплата: 10 токенов пользователю 42 (пользователь создаётся первой оплатой)
BODY='{"payment_id":"pay-1","user_id":42,"tokens":10,"status":"succeeded"}'
curl -s $API/webhooks/payments -H "X-Signature: $(sign "$BODY")" -H 'Content-Type: application/json' -d "$BODY"
# {"credited":true}; повтор того же запроса даёт {"credited":false}

# 2. заказ (image-fast стоит 2 токена)
curl -s $API/generate -H 'Content-Type: application/json' \
  -d '{"user_id":42,"model_slug":"image-fast","prompt":"cat","ref_images":[]}'
# {"task_id":"<uuid>"}

# 3. статус и история попыток (фейк отвечает через 2-20 с)
curl -s $API/tasks/<uuid>
curl -s $API/users/42/balance
```

Ответы `/generate`: 202, 400 (неизвестная модель или ни одна нога не принимает столько референсов), 402 (мало токенов), 404 (нет такого пользователя), 422, 429 (уже 3 активные задачи). Остальные ручки: `POST /webhooks/providers/{name}`, `GET /tasks/{id}`, `GET /users/{id}/balance`.

## Тесты

```bash
docker compose up -d --build --wait
docker compose --profile test run --rm tests pytest -v
```

Сервис `tests` лежит в compose-профиле `test`, поэтому обычный `up` его не запускает. Тесты ходят в настоящие `db`, `api` (4 воркера) и фейки. Всего 59 тестов: 48 e2e (`tests/e2e`, против живого compose) и 11 для самих фейковых провайдеров (`tests/test_fakeprovider.py`). Среди них, кроме обязательных, есть гонка первой оплаты для ещё не существующего пользователя (`test_concurrent_first_payments_for_new_user`), 429 и 402 под гонкой и сторож против вебхука.

Набор идёт около 90 с. Почти всё время это обязательный тест №4: он честно ждёт `PROVIDER_TIMEOUT=60` с, пока сторож сдастся. Остальные тесты, где сторож не главный герой, сдвигают дедлайн попытки в БД.

Обязательные тесты из ТЗ:

| № | Что | Тест |
|---|---|---|
| 1 | 20 одновременных одинаковых вебхуков оплаты дают одно начисление | `tests/e2e/test_payments.py::test_twenty_concurrent_payment_webhooks_credit_once` |
| 2 | 10 одновременных `failed` на последней ноге дают один возврат | `tests/e2e/test_failover.py::test_ten_concurrent_failed_on_last_leg_refund_once` |
| 3 | Отказ первой ноги: завершение на второй, две попытки в истории | `tests/e2e/test_failover.py::test_first_leg_fails_second_completes` |
| 4 | Поздний `completed` после сторожа (правило 6) | `tests/e2e/test_watchdog.py::test_late_completed_after_watchdog_gave_up` |

Фикстура `balance_invariant` (autouse, `tests/e2e/conftest.py`) после каждого теста проверяет, что баланс каждого пользователя равен сумме его журнала.

`./run.sh` в корне делает похожее в одну команду (но только `tests/e2e`): если `.env` нет, молча создаёт его с `DB_PORT=55432`, поднимает `db migrate api alpha beta` и гоняет только `tests/e2e` (без `--profile test` и без `tests/test_fakeprovider.py`).

Локально (сервисы подняты в compose, порты проброшены на хост):

```bash
pip install -e '.[dev]'
DATABASE_URL=postgresql://app:app@localhost:5432/app WEBHOOK_SECRET=test-secret PROVIDER_TIMEOUT=60 \
API_URL=http://localhost:8000 ALPHA_URL=http://localhost:8001 BETA_URL=http://localhost:8002 pytest -v
```

(подставьте свои порты, если переопределяли; если `./run.sh` создал `.env`, БД на хосте слушает `55432`, и `DATABASE_URL` должен быть с этим портом.)

## Миграции

Файлы `migrations/NNNN_name.sql` применяются по порядку раннером `python -m app.migrate`. Он берёт `pg_advisory_lock` (параллельные запуски идут по очереди), ведёт таблицу `schema_migrations` и выполняет каждый новый файл вместе с записью о нём в одной транзакции. В compose это сервис `migrate`: `api` стартует только после его успешного завершения (`service_completed_successfully`).

Следующая миграция: положить `migrations/0003_<что>.sql` и выполнить `docker compose run --rm --build migrate` (или `docker compose up --build`). `--build` обязателен: у `migrate` нет volume, `COPY . .` в `Dockerfile` запекает `migrations/` в образ, и без пересборки `docker compose run --rm migrate` печатает `applied: nothing`. Применённые файлы не трогать. Каталог моделей и ног лежит в `0002_catalog.sql`.

## «Ровно один раз»: начисление и возврат

**Журнал единственный способ изменить баланс.** Таблица `ledger` (`migrations/0001_schema.sql`):

| Механизм | Что гарантирует |
|---|---|
| `UNIQUE (payment_id)` | одна оплата, одно начисление (у списаний и возвратов `payment_id` NULL, они не конфликтуют) |
| `UNIQUE (task_id, reason)` | у задачи не больше одного списания и не больше одного возврата |
| `CHECK` на знак и на заполненность `payment_id`/`task_id` по `reason` | нельзя записать возврат отрицательным или оплату без `payment_id` |
| триггер `AFTER INSERT ON ledger` | `users.balance += amount`. В приложении нет ни одного `UPDATE users SET balance`, правило 8 держит БД |
| триггер `BEFORE UPDATE OR DELETE ON ledger` | журнал только дописывается |
| `users.balance CHECK (balance >= 0)` | последняя защита от ухода в минус |

**Начисление** (`app/money.py: credit_payment`), одна транзакция: `INSERT INTO users ... ON CONFLICT DO NOTHING`, затем `INSERT INTO ledger ... ON CONFLICT (payment_id) DO NOTHING RETURNING id`. 20 одновременных доставок ждут друг друга на уникальном индексе, строку получает одна, остальные видят пустой `RETURNING` и отвечают `{"credited": false}`. Дубль откатывает транзакцию целиком, поэтому повтор `payment_id` с чужим `user_id` не оставляет «пустого» пользователя.

**Возврат** (`app/orchestrator.py: finish_failed`, `app/money.py: refund_task`) двойная защита:

1. условный переход `UPDATE tasks SET status='failed' WHERE id=$1 AND status='running' RETURNING id`, выполненный под блокировкой строки задачи (`SELECT ... FOR UPDATE OF t`). Возврат запускает только тот, кто реально совершил переход, поэтому он срабатывает один раз сколько бы вебхуков ни пришло;
2. `INSERT INTO ledger ... SELECT user_id, -amount, 'refund', task_id FROM ledger WHERE task_id=$1 AND reason='charge' ON CONFLICT (task_id, reason) DO NOTHING`. Даже ошибка в коде не даст второй возврат: его не пропустит уникальный индекс. Сумма берётся из строки списания, так что смена цены в каталоге возврат не ломает.

Списание (`create_task`) защищено иначе: условного перехода здесь нет (он только у возврата). Списание создаётся в одной транзакции с совершенно новой задачей под блокировкой строки пользователя, а `UNIQUE (task_id, reason)` не даст списать по ней дважды.

## Падение процесса посреди обработки вебхука

Обработка вебхука это одна транзакция: смена статусов, строка журнала, создание следующей попытки. HTTP к провайдеру никогда не делается внутри транзакции и под блокировкой.

| Где упали | Что будет |
|---|---|
| до `COMMIT` | PostgreSQL откатывает всё, состояние как до вебхука. Если провайдер повторит доставку, она обработается с нуля. Если не повторит, задачу по дедлайну дотянет сторож |
| после `COMMIT`, до ответа 200 | провайдер повторит доставку, она станет no-op: условные переходы (`status='running'`, `current_attempt_id`, `status IN ('dispatching','pending')`) и `ON CONFLICT` ничего не изменят |
| после `COMMIT`, до HTTP-отправки следующей ноги | новая попытка осталась в `dispatching` со своим `deadline_at`. Через `PROVIDER_TIMEOUT` сторож засчитает её неудачей (`timeout`) и поведёт задачу дальше. Повторной отправки той же ноги нет (тест `test_orphaned_dispatching_attempt_recovered`) |

Инвариант (обеспечивается кодом приложения): у `running`-задачи, как правило, есть текущая незавершённая попытка (`dispatching` или `pending`) с дедлайном в БД, поэтому задача не должна зависнуть навсегда. На уровне БД закреплено только одно: частичный уникальный индекс `attempts_one_live_per_task` не даёт иметь больше одной такой попытки на задачу.

## Правило 6: поздний `completed` после сторожа

«Сторож сдался» может значить два случая, решение принято для каждого:

| Ситуация | Решение |
|---|---|
| Сторож снял последнюю ногу, задача `failed`, возврат сделан, потом пришёл `completed` | **Результат игнорируем, возврат остаётся.** Задача `failed`, `result_url NULL`. Попытка получает статус `late_completed` и хранит ссылку для аудита. Ответ 200, чтобы провайдер не повторял доставку |
| Сторож перевёл задачу на следующую ногу, задача ещё `running`, пришёл `completed` от прошлой ноги | **Результат принимаем.** Задача `completed`, текущая попытка `abandoned`. Возврата не было и не будет: задача терминальна. Принявшая попытка сохраняет прежний `error_type` (`timeout`), статус у неё `completed` |
| Повторный или запоздалый `completed` по уже `completed` задаче | Другая попытка получает `late_completed` (ссылка в истории, задача и деньги не меняются). Дубль от победившей попытки: no-op |

Почему не «отдать результат и отменить возврат»: это третье движение денег по задаче. Пользователь мог уже потратить возвращённые токены, и повторное списание либо уведёт баланс в минус (нарушит `CHECK`), либо не пройдёт, и результат уйдёт бесплатно.

Гонка «`completed` одновременно со сторожем» снимается блокировкой строки задачи: оба пути берут `SELECT ... FOR UPDATE OF t` и перепроверяют статус после неё. Кто первый, тот и определяет исход, а результат вместе с возвратом получить невозможно (тест `test_completed_races_watchdog_never_both`).

## Конкурентность и сторож

- **`/generate`** (429/402 без гонки). Транзакция начинается с `SELECT ... FROM users WHERE id=$1 FOR NO KEY UPDATE`; под ней проверяются лимит активных задач и баланс, затем идут создание задачи, списание и первая попытка. Параллельные заказы одного пользователя, даже на разных воркерах, проходят по очереди, поэтому гонки на 3 задачи и на баланс нет. `NO KEY UPDATE` не конфликтует с `KEY SHARE` от FK-проверок, `SERIALIZABLE` не нужен.
- **Сторож** работает в каждом из 4 воркеров, лидера нет. Выбор: `SELECT a.id FROM tasks t JOIN attempts a ON a.id = t.current_attempt_id WHERE t.status='running' AND a.status IN ('dispatching','pending') AND a.deadline_at < now() ... FOR UPDATE OF t SKIP LOCKED`. `SKIP LOCKED` раздаёт разным процессам разные задачи; а `fail_attempt` после блокировки перепроверяет состояние, так что вебхук или другой сторож, успевший раньше, превращает шаг в no-op. Тест `test_watchdog_does_not_double_advance`.
- **Залипания нет.** Дедлайн хранится в БД и сравнивается с `now()` БД: часы процессов не участвуют. Упавший процесс снимает блокировки откатом, задачу подберёт любой другой сторож.
- **Единая точка перехода.** Вебхук `failed`, синхронная ошибка отправки (5xx, таймаут, сетевая ошибка) и сторож все идут через `fail_attempt`. `failed` от устаревшей попытки (не текущей) игнорируется.

## Допущения и решения

| Вопрос | Решение |
|---|---|
| Правило 6 | таблица выше |
| Неизвестная модель в `/generate` | 400, как и «нет подходящей ноги»: до списания, ничего не блокируется |
| Порядок отказов в `/generate` | модель/ноги 400, пользователь 404, лимит 429, баланс 402. 429 раньше 402: пополнение пользователю с тремя активными задачами не поможет |
| «Активная» задача | в статусе `running`. Четвёртая одновременная получает 429. Лимит 3 это константа `MAX_ACTIVE_TASKS` |
| `skip_on_moderation` | нога пропускается, если **любая** прошлая попытка задачи отказала по `moderation` (а не только предыдущая): модерация свойство содержимого, оно не меняется. «Пропуск» значит перейти к следующей ноге. В текущем каталоге из 2 ног оба прочтения совпадают. Отказ `technical` ногу не пропускает |
| Идемпотентность `POST /generate` | **не делается:** каждый вызов новый заказ и новое списание. Путь расширения: заголовок `Idempotency-Key` и `UNIQUE (user_id, idempotency_key)` в `tasks`; повтор с тем же ключом возвращает существующий `task_id` |
| Поле `status` оплаты | начисляет только `succeeded`, остальное даёт 200 `{"credited": false}` без строки журнала. Chargeback вне объёма ТЗ |
| Повтор оплаты с другим телом | выигрывает первая доставка `payment_id`, остальные no-op. Отвергнутый дубль не создаёт пользователя |
| Откуда пользователи | регистрации нет, пользователь создаётся первой оплатой; `/generate` и `/balance` для неизвестного дают 404 |
| Синхронная ошибка отправки | 5xx, таймаут (`PROVIDER_HTTP_TIMEOUT`, 5 с) и сетевая ошибка ведут на следующую ногу. Ответ 202 без внятного `external_id` тоже считается ошибкой |
| Вебхук раньше ответа 202 | попытка ищется по нашему `reference`, а не по `external_id`, поэтому гонка безопасна |
| Неверная подпись | 401 без разбора тела и без изменения состояния. Подпись считается по сырым байтам до разбора JSON |
| Приоритеты в каталоге | числа в ТЗ не даны: 1, 2 в порядке таблицы, меньшее пробуется раньше |
| Код ответа `/generate` | 202: задача асинхронная |
| Пользователь при `late_completed` | результата нет (`result_url NULL`), ссылка только в истории попытки. Пользователь получил возврат |
| Повторная отправка той же ноги после падения до HTTP | не делается: `dispatching` после дедлайна засчитывается как неудача (правило 5) |
| Фейковые провайдеры | одно приложение (`fakeprovider/`), один воркер на контейнер (режим в памяти, для двойника допустимо). Задержка 2-20 с настраивается, режимы (отказ, 503, таймаут, дубль вебхука, молчание, поздний `completed` при `delay_min` > `PROVIDER_TIMEOUT`) переключаются через `PUT /_admin/config` и `POST /_admin/reset` |
